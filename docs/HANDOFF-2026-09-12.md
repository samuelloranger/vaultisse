## ⚠️ Do not deploy HEAD as-is

Two reasons, both real:

1. **The server has an admin gate whose client half is uncommitted.**
   `9bb82fb` put `requireAdmin` on the lending toggle, but the UI change that
   moves that card off the Profile screen is still in the working tree. At HEAD,
   a non-admin still *sees* the Lending card and gets a **403** when they touch
   it.

2. **`assets/db/upgrade/1.3.0/1.sql` has NOT been applied to production.**
   `62bc5bf` reads `app_settings.registration_requires_approval`,
   `default_language`, `default_region` and `default_theme`. Those columns exist
   in the **dev** database only. Deploying HEAD to prod without running that
   migration first means `POST /register` 500s.

   The migration lives under `1.3.0/` and not `1.2.0/` deliberately — 1.2.0 has
   shipped and been applied, and applying is manual and per-file with no runner
   recording what ran, so a file added to a finished version is a file nobody
   runs. The reasoning is in the file's own header. A half-migrated production
   database already happened once today; don't repeat it.

Either finish the client half and deploy both together, or revert `9bb82fb`
before deploying. Do not deploy one without the other.

## Standing rule from the owner

**Never invent data.** Stated emphatically today: *"do NOT invent data!!! if it
does not exist or is just a number, do not add it or link it to something that
does not exist, I'll rework that later."*

No placeholder categories, no `"Uncategorised"` default, no category name
derived from BnF's numeric `686` class code, no publisher inferred from an
imprint, no language guessed from an ISBN prefix. If every source is silent, the
field stays NULL and the UI says nothing was found. "Nothing new was found" is a
correct, reportable outcome.

Context: the owner's four books have **no category in any source** — Google
returns `categories: None` for them, and the BnF records carry no `606` subject
heading on fiction. Categories there are a manual job and the owner has said
they will do it themselves.

## Known limitations worth not rediscovering

- One category per book (`books.category_id` is a single FK). No genre table.
  Genre would need a many-to-many; the owner said to drop it for now.
- `format_id` (Paperback, Hardcover, …) is never supplied by any source — manual
  only.
- Google's `categories` is `['Fiction']` for both *The Hobbit* and *Dune*, i.e.
  useless as a genre. Open Library's `subjects` are richer but noisy
  (`thrushes`, `New York Times reviewed`), and the chain takes `categories[0]`.
- `server/test` agents collide: `preload.ts` drops and recreates the same
  `vaultisse_test` database. Always run with `TEST_DB_NAME=<unique>`.
